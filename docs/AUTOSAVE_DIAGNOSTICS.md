# 播放与草稿保存回归验证

针对播放后点击时间线无响应、同时出现“草稿保存失败”的反馈，分别检查媒体资源占用、草稿写入和失败后的恢复。

## 测试工程

- 单视频工程：3024 × 1896、30 fps、70.3 秒；同一视频拆成 16 段，另有 46 个文字片段和 8 个转场，共 70 个片段。原视频约 54.6 MB。
- 多素材工程：40 份实际编码视频与 20 份 PCM 音频，共 60 个素材、61 个片段，媒体合计约 53.2 MB。
- 工程通过真实便携项目导入，使用实际媒体解码和本地数据库；检查重载后的内容及媒体 SHA-256。

## 已确认的问题与修改

| 检查项 | 修改前 | 修改后 |
| --- | --- | --- |
| 单视频工程播放时常驻的预览视频元素 | 16 个载入同一原件 | 当前片段及附近片段，实测 1–2 个 |
| 单视频工程修改名称后的原件读取／重写 | 各 54,575,686 字节 | 均为 0 |
| 60 素材工程修改名称后的原件读取／重写 | 各 53,231,760 字节 | 均为 0 |
| 保存未完成时又连续修改的写入次数 | 测试中积压 3 次 | 当前写入加最新等待版本，共 2 次 |

这些原件读写数据针对由 Blob 保留素材的工程，包括便携项目恢复和网页导入。使用持久本地路径、未提供 Blob 的素材本来就不会在每次保存时复制原视频。

草稿现在只写入新增或变化的媒体，未变的媒体仅检查键是否存在。媒体缓存与已提交版本绑定；失败的事务不会被当作成功缓存。同大小的替换文件、撤销、缺失记录和删除后重建均有覆盖。

预览只保留当前及附近片段，离开播放范围后释放媒体元素；素材列表只加载可见缩略图。连续视频分段保持解码衔接，重叠片段仍使用独立播放源，导出准备阶段仍检查完整媒体。

保存队列合并尚未执行的旧版本；旧保存的成功或失败不会覆盖新修改的状态。最近项目列表刷新独立于写入完成，同版本重复请求也会正确结束“保存中”状态。撤销回文件已保存状态后，切换或关闭仍会保留最新草稿，避免较旧的在途写入覆盖撤销结果。

## 验证内容

- 单视频工程连续播放约 42 秒，期间自动保存；随后 15 次视频、文字、转场选择与跳转，未出现永久无响应。
- 纯播放、选择和跳转没有触发草稿写入。
- 注入存储空间不足及真实事务中止：保留原草稿、原保存时间和全部媒体，界面仍可操作，重试后可重新载入。
- 延迟旧写入完成或失败，再提交新编辑：最终保留最新内容，状态不被旧结果覆盖。
- 实际 WebKit 持久浏览器上下文：首次保存 60 MiB 媒体后，连续 10 次元数据保存不重复读写原件；重载、失败回滚、重试和媒体校验通过。
- 视频分段衔接、音频连续播放、文件保存及另存为、保存时间、关闭保护另有回归检查。

## 复跑

先安装项目依赖、测试浏览器及 FFmpeg。以下命令启动开发测试服务，不打包应用：

```sh
npm test
npm run test:autosave
npm run test:autosave:large
npm run test:storage:webkit
node tests/browser/project-save-status.cjs
node tests/browser/project-save.cjs
node tests/browser/native-close.cjs
```

可通过 `BROWSER_EXECUTABLE` 指定测试浏览器，通过 `BROWSER_ARTIFACTS` 指定截图、报告与测试工程保存目录。高分辨率工程首次运行会生成实际视频，耗时较长；性能对比应顺序运行，避免其他编码任务争抢资源。

## 结论范围

修改前、修改后的单视频测试都没有复现用户报告的永久卡死。以上结果确认并修复了重复媒体加载、整份原件反复写入和保存状态竞态，但不能把资源优化直接当作已定位原机卡死的全部原因。测试环境为 Linux 浏览器；WebKit 存储测试不等同于 macOS 安装版真机测试。尚未获得用户原工程和该次草稿失败的具体错误。
