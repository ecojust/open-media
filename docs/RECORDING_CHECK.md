## 授权范围补充

上述检查由构建脚本直接启动安装目录下的录制模式。构建机镜像预先给执行代理配置屏幕访问授权，因此实际视频能够证明采集、编码、红框和停止清理成功，不能证明用户通过应用图标启动后的授权归属，也不能证明升级后旧授权可继续使用。专项流程在 macOS 26 上另外编译应用，同样不能替代对正式下载包原样安装的检查。

当前正式包使用临时签名。应用标识保持不变，并不保证每次更新后的代码签名要求与之前相同。如果升级后出现 `-3801`，而系统设置中仍显示已授权，请完全退出应用，在屏幕录制权限列表中移除旧项目，再添加 `/Applications/Open Media.app` 中的当前副本并重新启动。这个恢复步骤需要用户在系统设置中明确完成；应用和测试不会自动重置权限、放宽签名要求或修改权限数据库。若重新授权后仍失败，需要继续检查当前安装副本的签名和系统拒绝记录。

`capture-gui-macos.yml` 专门检查已有正式包：校验下载文件，保持原签名安装，通过正常应用启动器打开工作台，再由外部测试驱动点击录屏、选择屏幕、开始和停止。驱动区分系统拒绝与无权操作界面等测试环境限制；只有界面报告完成且新保存的视频通过实际解码，才报告成功。证据包括界面可访问性树、阶段截图、进程父子关系、系统权限日志、代码签名要求及视频。构建机本身仍可能具有额外授权，必须结合责任进程记录分析，不能据此承诺用户机器或历史升级授权已验证。

这次测试验证了正常应用与执行代理的授权区别，正确保留为未授权失败，没有将它报告为成功录屏。它没有验证用户 macOS 26.5 的实际授权记录、升级历史或移除旧条目后重新授权的结果，不能将全新环境的未授权拒绝当作“已授权后仍失败”的回归证据。保留旧授权直接升级的情况，仍应先在系统设置中重新授权当前安装副本，再验证录制。

## 麦克风签名声明修复

2026-10-17，用户报告 `v0.1.8` 开始录制时提示“麦克风访问被拒绝”，且系统麦克风权限列表没有 Open Media，也未出现授权弹窗。复核该版本发现，应用已有 `NSMicrophoneUsageDescription`，但强化运行时签名仍未包含上文记录的 `com.apple.security.device.audio-input` 声明；此前关闭麦克风的录屏检查未覆盖这一缺陷。

已在源代码中添加麦克风签名声明，并保持强化运行时开启。打包检查将读取最终主可执行程序的签名，核对音频输入声明和应用权限用途说明；声明缺失或未启用时应阻止发布。此检查不采集音频，也不会批准系统授权。

此修复随 `v0.1.9` 打包；发布要求两种 macOS 架构的最终应用签名检查通过。签名检查不等于用户设备实测：尚未在用户的 macOS 26.5 上验证授权弹窗和实际麦克风采集。安装包含此修复的版本后，仍需用户明确允许麦克风访问，再验证录制文件中的声音和停止后的设备释放。
